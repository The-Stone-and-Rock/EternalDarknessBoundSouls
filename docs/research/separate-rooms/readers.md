
######## room-memory
The game keeps exactly ONE room resident, by a constant, inside an engine that was written for N slots. At play start (0x80020EB4) it takes one OSAlloc block (r13-25984, ~9.18 MB: one room slot of 2,916,384 bytes = 0x801538AC() x 0x8004304C() slots, where 0x8004304C is `li r3,1`; plus a 1,921,024-byte model area, a 335,008-byte per-slot area, and the 0x3D3100 level bump heap at r13-23736). Every room-slot function (0x80154C94, 0x80154C50, 0x80153C68, 0x80155130 section 3 = "the other slot") already carries the two-slot logic (table 0x8058AFC0: +0 current slot, +4 other slot or -1, +12.. slot records), gated on that count being 2. Room files (Rooms/rmedNNNN.bpe, BPE-compressed, 49 KB to 1.68 MB on disc, 79 KB to 2.68 MB unpacked, mean 1.6 MB) are prefetched from the disc into an ARAM cache of 2 entries x 1,677,824 bytes at ARAM 0x600000 (fn71 and the exits list 0x80154B54 ask for them; the reader thread 0x801531CC streams 32 KB pieces by ARQPostRequest), and a room change unpacks ARAM -> the one RAM slot (message 0x4000|room, 0x80154118). The change itself is synchronous: 0x80152298 waits for the GPU (GXReadDrawSync 0xBEEF), pauses the animation streamer (0x8012EDC0), marks the slot's record (room s16 at +0x8140, loaded byte +0x8142 := 0), posts to the slot thread (queue 0x805B27BC) and blocks in OSReceiveMessage on 0x8058B028 until the reader has unpacked (then 0x80151FDC: fade in, placings per node 0x80043A5C, event 61 to the OLD room's nodes, prompt slots reset 0x801172B0, busy cleared, 0x80152614 then places the player, event 238, event 62 to the NEW room's nodes, the camera, the script). In this recomp the whole change took 3 to 4 timebase frames in logs (room 103, 2.59 MB: change at frame 1070, arrival script at 1074). Nodes of ALL rooms live in one list, each with a room word (0x801F662C; broadcasts filter by it, fn78 kind 2 vs 4), and the player's room is object +592 (COOP_OBJECT_ROOM); the one global "room in play" is r13-23276 (15 writers, 675 readers; r13-23288 the old room). The level's scripts, words, flags, carried lists, the Tome and the element pool persist across rooms. The host already extends guest RAM to 48 MB (cpu.c:27) with the game's 24 MB untouched, scratch at 0x81800000-0x82000000, the Tome's room buffer at SCRATCH_TOME 0x82000000 and the detail pools at 0x82800000, so a second 2.9 MB room slot has physical headroom [inf]; the Tome copy (tome_copy_step) is a full memcpy of cpu->ram_size (48 MB), swapped in by one pointer plus the 0x4F8-byte GX record, run as guest calls with no interrupts, not copying ARAM, host state or the renderer's caches, and thrown away at close.

## hard
- ONE slot by a constant: the whole room system (0x80154C94, 0x80153C68, 0x80155130, 0x80154C50, the reader's 0x4000 branch via r13-23304[slot]) indexes slots, but 0x8004304C returns 1 and the block at r13-25984 is sized for one slot (ed dis 0x80020EC0: mullw by 0x8004304C()). Making it 2 means a second 2,916,384-byte slot plus a second 335,008-byte area in the block (or in the host's extension), and every per-slot caller must then run its 'other slot' branch, which has never run in this game.
- ONE 'room in play' word read 675 times: r13-23276 feeds fn25, fn78 kind 2, the zone scan (0x80123F70's list is the current record's), the broadcasts (events 61/62 filter by room), the prompt slots, the camera records, the lights grid (0x804F0784), the sanity list, collision and geometry pointers set at 0x80151FDC (0x801E1B74(record+0x813C)). Two rooms need either both records live and every reader told which player's room it serves (the 'ed needs' pattern), or the renderer drawing a second record it has no pointer for. Evidence: grep -c '-23276(r13)' = 675; ed dis 0x80151FDC.
- The change is SYNCHRONOUS and stops the whole game: 0x80152298 waits on GXReadDrawSync, stops the background thread (0x80042910), fades sound, blocks the game thread in OSReceiveMessage(0x8058B028) until the unpack is done, and GXInvalidateTexAll's the renderer; it also pauses the animation streamer (0x8012EDC0). For one player to change room while the other walks, the other's frame must survive this block (today coop_follow brings them along instead). Evidence: ed dis 0x80152298 0x80152370-0x8015239C.
- The change tears down the other player's room: 0x80043820 unloads the moves/parts of every character not in the NEW room (0x800438AC-0x800438F8), event 61 goes to the OLD room's nodes (0x801520F4), the camera records are reset (0x801EB7A0), the prompt slots cleared (0x801172B0), busy cleared for everyone (0x801556CC(-1,0)), and the one slot record's room id becomes the new room, so the old room's zones, markers, collision and geometry are gone from memory the moment the unpack overwrites the slot.
- Rooms share ONE light grid pointer (0x804F0784) that already flips between two grids near a door; room_lights_update holds the room's own (hle.c:6064-6080). Two live rooms means two grids, two sets of lamps, and the renderer's shadow/haze pass taking lamps per view.
- The ARAM cache has 2 entries (0x80043044 = 2) of 1,677,824 bytes at ARAM 0x600000; its prefetch list is the current room's exits (0x80154B54). Two players in two rooms double the prefetch candidates and halve the hit rate; a miss means a disc read inside the change (cheap in this recomp: a host file read).
- The Tome already borrows the room's memory in solo (packs the room away and 0x80152298(current, 76) reads it back; tw_keep/tw_room_buffer route it to SCRATCH_TOME instead): any second-room buffer must stay clear of the Tome's own packing path and of SCRATCH_TOME (0x82000000 + TW_TOME_MEMORY) and the detail pools (0x82800000).
- The Tome copy approach (a second world in a copy) is 48 MB per copy, 3 to 7 ms to make, and the copy's turn skips interrupts and frame waits; its design doc lists the room change itself among the things that CLOSE the copy ('a door, cutscene, death, room change ... closes player 2's Tome with no harm'). A copy running a whole other room would need the renderer to draw both memories in one frame (dol_aurora_mem1_turn switches the whole renderer's memory per frame today), sound from one memory only, and the two node lists would never see each other (items picked up, flags set) without a merge step the Tome copy avoids by sending chosen effects only.
- Many host range checks treat 0x81800000 as the game's end (hle.c:5409, 6057, 6061, 6074, 6151, 6618): a room record placed in the extension would be rejected by them until they are revisited.

######## render-split
The game draws ONE scene per frame and the host turns it into two halves after the fact: the renderer records every uniform upload and draw of the game's frame (interp.cpp note_uniform/note_draw) and, for each player, replays the whole recorded packet once more with every perspective projection rewritten for that player's camera (split_build -> build_view -> encode_between), then draws the game's own frame a third time so its EFB copies stay the game's. Nothing in the pipeline knows about rooms: a half is "the same draw list from another eye". Player 2's camera is expressed relative to the game camera's view space and queued in the GX stream (dol_aurora_split_set_view) so it lands on the frame it was computed for. Per-half HUD is done by the game drawing player 2's elements 4096 units off the right and build_view sliding them back; per-half 3D exclusion is done by three marker bytes in a matrix's translation (coop_found_mark / marked_out_of). Lights and shadows are per frame, not per view: one room grid (0x804F0784) is uploaded, the shadow camera is the frame's first scene draw's matrix (gxcore_draw.cpp:2133), and each view re-derives pixel positions from its own projection. Co-op is capped at 60 (settings.c:349) because the current 3 full redraws per game frame (5 with in-between moments) already don't fit 16.7 ms on this PC. The Tome copy is the only existing case of two different "worlds" on screen: it runs the Tome's frame in a full copy of RAM (memcpy of ram_size at open, a pointer swap + dol_aurora_mem1_turn per turn), tagged with split_skip_views so the renderer keeps that frame's picture (s_menuKept) and fits it into the owner's half while the other half shows the world from the other player's camera (aurora.cpp:930-1010). It alternates the copy's frame with the world's: the world's frames keep the retrace wait, the copy's wait for nothing. For two rooms: (a) two scenes in one game frame has nothing built — the game has one room buffer (rooms load at the same place, r13-25984; the next room preloaded lies after it and is only read for its light grid), one behaviour-list draw pass (0x8014FE24 -> 0x8014F3E8(beh,2,80)), one camera stack, and the recorder/replay assume one projection family per frame; (b) alternating frames as the Tome copy does already has the frame-splitting, memory-swapping and per-half-picture machinery, but a second resident room would mean a second full memory image walking its own room each frame, with its own room load, lights, sound and object lists, at roughly double the game-side cost and another full render of a different packet; (c) a different memory image per half is (b) seen from the renderer: g_mem1 already switches per op in the GX stream (mem1_turn_op), textures are keyed by content hash, so the renderer side is mostly there; the open questions are the game side (two loaders, two light grids, two sound sets, whose busy word) and the fade, which is a game-drawn screen-wide quad plus VISetBlack, so today it blacks both halves; aurora_split_hold can freeze one half on its last picture and viBlack is honoured per present, but there is no per-half fade.

## hard
- One scene per frame is baked into the whole picture path: the recorder keeps one draw list and one set of uniforms per frame (interp.cpp g_frames[g_cur]), build_view rewrites EVERY perspective projection to one PhotoView, and encode_between replays the WHOLE packet per view (common.cpp:2196-2214, :2458-2487). A second room's geometry inside the same frame would be re-projected into both halves unless every one of its draws were marked out of the other view, and the only exclusion mechanism is the three-byte matrix mark on an object's modelview (coop_found_mark / marked_out_of), which applies to objects drawn through 0x8011A278, not to room geometry.
- The game keeps one room buffer: rooms load at the same place (r13-25984, hle.c:6066-6069), the room change runs with the old room still in (hle.c:11127), the Tome reuses the room's data buffer (TW_ROOM_BUFFER 0x801538A4, hle.c:13045-13066), and events 61/62 go to nodes in the old/new room (transitions.md:204-236). A second resident room means a second buffer, a second loader result and two sets of nodes for one behaviour-list draw pass 0x8014FE24 -> 0x8014F3E8(beh, 2, 80).
- Lights and shadows are per frame: one light grid pointer 0x804F0784, one upload per grid change (room_lights_update, hle.c:6047-6124, dol_aurora_set_room_lights), one shadow camera g_sh.view taken from the frame's first scene draw (gxcore_draw.cpp:2133-2136), and the lamp set remembered across frames (kFlatMemory, g_slots). Two rooms in one frame would need two grids and two 'first room draws', and near a door the pointer already flips between two grids, which the host actively suppresses.
- Frame budget: co-op already does 3 full renders per game frame (view 0, view 1, the game's own hidden frame) and is capped at 60 because 5 did not fit 16.7 ms on this PC (settings.c:346-349, coop-failed-attempts.md:376-383, glitch-todo G1). Any approach that adds a second scene adds at least one more full render of a DIFFERENT packet per game frame (two scenes: 2 views + 2 hidden frames = 4; alternating: the second image's own frame every round, so the game side roughly doubles too). [inf] On this machine that is the difference between 60 and the ~50 Hz slowdown already seen.
- The fade blacks both halves: the fade is a screen-wide game draw kept in both views (interp.cpp:234-251, :598) and VISetBlack is one latch honoured per present (hle.c:3657-3659, aurora.cpp:616). One player's door would black the other's half; the only per-half tools are aurora_split_hold (freeze on the last picture, which the user has ruled out as a fix) and leaving a view out (only_view), neither of which is a fade.
- Culling: the draw list is ordered by distance to player 1's shown eye 0x806037D8 and whether 0x8011A278 culls to player 1's frustum is unread (coop-level3-design.md:971, :1412; :830 calls it known). If it culls, a room drawn for player 2 far from player 1's camera would already lose objects in player 2's half, before any second room.
- Player 2's own camera set (COOP_ZONE_CAMERAS 0x80602B18..0x8060394C, depth r13-21700, index r13-26864; hle.c:14325-14342) is swapped in and out of the SAME game memory each turn, and its records are picked from the room's own camera array (ed room N). In another room that set would have to be fed from a room file the game does not have loaded.
- The Tome copy's alternation works because the Tome's frame is nearly all 2D and small (graphics.md: 'The Tome's frames are flat, with too few 3D draws to run effects') and because nothing in it moves the world (tw_keep passes over the room pack/readback, motion let-go). A second WORLD frame in a copy would run the full behaviour step and draw for a second room, with its own interrupts/audio polling skipped (coop-two-tomes-design.md 'What the copy must not do'), and its sound would have to merge into the one speaker set (sanity.md:231: 'sound shares one set of speakers').
