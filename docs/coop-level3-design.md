# Co-op level 3: examine, words and pickups by both players at once (design round 1, 2026-11-10)

Written from a reading pass (four readers on the game's machine code and the host) and one design, then two adversarial
reviews, all on 2026-11-10 evening. **Round 1 is refuted**: the design's mechanism (one per-player block swapped at the turn,
the game's holds run natively) breaks what works today, for reasons the reviewers read in the code. The refutations are
the specification for round 2. Nothing of this is built. The gate list for a close-up and a find beside a scene (the
afternoon's reading) is in `docs/coop-todo.md` and the scratchpad's closeup-gates.txt of that session.

## What the readers established (summary; the full reports are below)

- The close-up stepper (0x80024D78..0x800255A4) keeps no statics of its own: its state is the look record 0x80307108 (68
  bytes), the camera set (record 10, the stack), the holds' words and the window. It is not stepped per frame: it is
  reached only from the prompt press (0x80006EBC), the words' close (0x80024220) and the find's close (0x80024434).
- The words window (0x80024310) lives at r13-25960 with its script at -25944 and closed-with at -25940, its text in a
  shared pool of ten elements (0x805F87D0, drawn every frame by 0x801DA574, each placed by its own +8 x: the split already
  shows an element in one half by x >= 4096), its input channel in whichever input copy is in, the focus at r13-23556.
- The find (0x80024528) gives the thing to the player, sends events 71/46/47/190, registers its own channel (0x80024434)
  and places the thing through 0x801FA400 -> 0x80119B94 into a per-frame draw list counted at r13-23956.
- The two Tomes are a full RAM copy with a mode loop (tome_copy_step), a hook-off list and a send-back list; the lighter
  pattern is a block swapped around a call (CoopPlayerState, coop_states_swap, coop_zones_swap, coop_cameras_lend).
- The split shows HUD elements per half by x and 3D draws per half by a matrix mark (coop_found_mark); the HUD's uniform
  block is shared across all text, so per-element x is per block, not per element.

## The round-1 design (refuted; kept as the record)

THESIS (answers the user's point). Nothing here needs a new engine mechanism. The host already owns the three things required: (a) a per-player state block swapped in and out around game calls (CoopPlayerState, hle.c:11798-11805, coop_state 12077; the 2060-byte r13-24040 block COOP_WORDS/COOP_WORDS_SIZE 11846-11847 swapped at 14802-14814, 18408-18409, 21899-21900; PROMPT_SLOTS/PROMPT_LOOKS and the camera set in coop_cameras_lend 14247-14300; SCRIPT_STATES in coop_states_swap 14342; zones in coop_zones_swap 14382), (b) a per-player turn in which the game's own functions run as player 2 (coop_player_turn 18268-18520: COOP_PAD_UPDATE 0x8013E518 and COOP_CONTROLLER 0x80045BC4 guest-called with player 2's pad and identity), and (c) a renderer that already shows a 2D element in one half by its x (kHudAway 4096: interp.cpp build_view 682-690; used by coop_prompt_show COOP_PROMPT_AT and the bars COOP_BAR_AWAY) and a 3D object in one half by a matrix mark (coop_found_mark 0xD2/0xA0+view/0xE5, hle.c:3270-3277; interp.cpp marked_out_of 565-572). What is wrong today is not a missing mechanism but a missing rule: ownership of the words/close-up/find is decided by heuristics (g_coop_screen, g_coop_assist_at, coop_their_close_up 16944-16952 testing g_coop_use/r13-21492/coop_close_up_p2s, coop_play_hold's lr-in-stepper test 12850, hle_coop_found's finder guess), each of which assumes one close-up at a time and routes player 2's presses through the game's single pad ("its DETAIL and words come by the game's own pad, as player 1's", 16946). The design replaces all of that with one rule: THE OWNER IS WHOSE BLOCK IS IN (g_coop_turn, already the flag for "inside player 2's turn", used at 16999/17003). Everything the game does with the words, the stepper and the find then happens twice a frame, once per block, in real memory, with no copy of RAM and no "send back".

(1) COPY MECHANISM, PER OBJECT, WITH REASON
- All four objects (close-up stepper, words window + text, find, shown prompt): PATTERN B, the block swap, extended to one union block ("scene block") swapped at exactly one place, coop_player_turn's in/out, with the few out-of-turn "as player 2" paths (coop_use_start 15931 / continue_coop_use 15977, tome_copy_left 23585, coop_prompt_look 14796) changed to call the same block function instead of their partial lists. Reason, read from the dossier: every one of these objects exists to have WORLD side effects while open (0x80024528 gives the thing to the player via 0x801F95A0 and sends events 71/46/47/190 through 0x801F57C0/0x801F59B0; the close runs 0x801642D4(script,0,id); the stepper pushes the shared camera stack; the holds write channel masks other systems read), and both game frames already step the words (0x80024AF0 at 0x800084FC and 0x80111484). Pattern A (the Tome's RAM copy, tome_copy_step 13527-13700) fits an object whose way out never needs to run and whose outputs are few and replayable at close (A10); here the outputs ARE the object, so a copy would need the growing send-back list docs/coop-two-tomes.md warns against, plus 40 MB per open, a hand-kept hook-off list (23746-23770) and no sound. The per-player state here is small and already enumerated: under 8 KB (list in (2)).
- Not even a hybrid is needed for drawing: the Tome copy's skip_views/only_view renderer path is for a frame that belongs wholly to one player; a words window and a close-up are a few elements plus a camera, which the split already handles per element (x >= 4096 -> player 2's half) and per camera (view 1 built from hle_coop_player2_camera, mode 2, camera.c:1700-1803). The one renderer addition is in (4).
- The one object kept SHARED on purpose: the element pool 0x805F87D0 (10 x 0x660) and the channel table slots inside COOP_INPUT (0x805880A0+176, 20 x 32). The pool is shared because 0x801DA574 draws all ten every frame and the renderer places each by its own +8 x; a per-player pool would force per-draw marking of text. The channel table is already per player because CoopPlayerState.input[816] holds the whole 0x805880A0 block, so player 2's words channel exists only while their input copy is in (the 0x8013DB3C make at 0x80024310 lands in whichever copy is in; 0x8013E518, guest-called in the turn at 18373, frees closed channels of that copy).

Every game function below runs either in the main frame (player 1's block is simply the game's memory) or inside the turn (player 2's block in). (4) DRAWING EACH HALF'S OWN WINDOW AND CLOSE-UP CAMERA
- Words/prompt elements: per-element by x, no double drawing. Player 1's elements stay at the game's x and are shown in view 0 only (view 1 has hideHud=true and only brings back offRight x>1 NDC, interp.cpp 682-697); player 2's elements get +8 += 4096 (hle_words_layout for words, coop_game_prompt_made / COOP_PROMPT_AT for prompts) and show in view 1 only. camera.c change: delete the g_coop_screen || hle_coop_cameras_lent() branch (1619-1663); always the normal-play branch (1700-1803) with view 0 hide_hud = hle_coop_player1_tome_up(), view 1 hide_hud = true. Both halves thus always own their HUD; "who owns the game's one HUD" stops existing.
- Close-up camera: player 1's is the game's camera (record 10 in the game's set, pushed at 0x80024E90/0x80025080). Player 2's is record 10 in THEIR set, pushed by the same stepper code in their turn, stepped by coop_camera_step in their turn, read by hle_coop_player2_camera (14550, mode mod_p2_camera 2) and turned by camera_split_update into view 1's rot/pos relative to the game camera. Nothing new in the renderer for the camera. Known cost (not new): the game culls to player 1's camera, so a close-up of something far from player 1 may show fewer objects in player 2's half (mode 2 limitation).
- The find's thing: the one aurora addition. 0x801FA400 places the thing in CAMERA space (0x80119B94(object,0,30000)); build_view re-projects world draws through the player's PhotoView, so an object placed relative to player 1's camera lands wrong in view 1. Add a fourth matrix mark (coop_found_mark writes e.g. m+15=0xD2, m+31=0xB0+view, m+47=0xE5 [inf]) meaning "player N's camera-fixed draw": build_view keeps it in view N with the identity PhotoView (zoom/aspect only) and collapses it in the other view. interp.cpp marked_out_of (565-572) + build_view 700-715 are the only renderer lines; then rebuild .deps/GXRuntime with VS2022 and regenerate patches/gxruntime/eternal-darkness.patch.

## What round 2 must take as given

1. The busy word gates the game's own loop (0x8000749C skips the player's controller, and so player 2's turn, while it is
   nonzero) and player 2's turn refuses on it (coop_player_turn). Any per-player busy must be answered from the *asked*
   player's block at those three asks (coop_busy_ask, the turn's refusal, coop_node_held_ask), or the other player freezes
   exactly as before coop_no_pause.
2. The 2060-byte block at r13-24040 is not swapped per player today (only saved and put back, and never its sound words
   r13-22920..-22396); it holds the busy word, the running script, the channel pointers, the focus, the prompt channel and
   the frame's draw-list count. It cannot be swapped whole.
3. Player 2's press on a prompt and the find's pickup run outside the turn today (coop_use_start at player 1's controller,
   the game's pad in a close-up of theirs); an owner rule keyed on the turn is wrong until those move into the turn, and
   moving them means tail calls become guest calls (a script that waits on a DVD read or a thread would stall the frame).
4. The turn overwrites player 2's channel masks and focus every frame on purpose (a lock and a focus kept for good); a
   window of theirs cannot keep its focus under that.
5. The lend and a whole-turn block cannot both own the camera set and the prompt slots; the lend's live-view carry must go
   somewhere; coop_camera_p2_in can rebuild player 2's set under a close-up.
6. 0x800255A4's return is load-bearing (cut vs blend); the find's thing is placed into a per-frame list in player 1's
   block, not in camera space.
7. The prompt chooser (0x80117628) is already hooked and guest-called by the host and refuses any prompt while any bit of
   r13-24048 is set; a per-player r13-24048 is required.

## The two approaches, named

- Approach 1 (today): answer the game's questions per player at each gate. General, cheap per gate, and every path finds
  its gates one at a time; the examine-and-pickup path touched eight of them in one afternoon.
- Approach 2 (the Tomes): copy the object per player and run the game against the copy. Complete once done; the Tomes
  took several sessions, a hook-off list and a send-back list.

Round 1 tried a third, the per-player block, and the reviews show it is approach 2 in disguise with approach 1's gates
still in the way. Round 2 should start from the seven points above and decide per object.

================================================================
WHICH FITS A PER-PLAYER CLOSE-UP + WORDS WINDOW [inferred]
================================================================
- Pattern A fits an object that is (1) the game's "paused solo" state by design, (2) self-contained (no world side-effects while open), (3) has FEW lasting outputs that can be read at close and replayed (Tome: equip, use-script+item, next cast, spell list; A10). The Tome's way out never has to run. Costs: a 40 MB memcpy per open (+ a second snapshot per player-1 Tome ask), one extra frame of CPU per world frame, a hand-kept hook-off list, callbacks/threads/FPU/GQR handling, no sound, and every lasting effect re-done in real memory with its own identity/zone/state/camera swaps anyway (tome_copy_left IS pattern B).
- A close-up / words window is the opposite kind of object: its whole point is a world effect while it is open (pickup -> carry list, flags, scripts' timers and callbacks such as the shelf's event 6, 0x801F7748; camera stack pushes; busy/hold bits that other systems read). In a disposable copy those would be lost or need a growing "send back" list — the loop the two-tomes doc warns against. Also both modes' frames already run the words (0x800084FC world, 0x80111484 Tome), and the per-player state is SMALL and already enumerated in code: window + script/button words (6 r13 words + 3 record words, tw_words_io), focus (2 words), prompt block r13-24040 2060 bytes, prompt slots 196 bytes, look record 68 bytes, camera set 0xE34+8, script states 80, CoopPlayerState 1916, busy/hold bits in -23344/-24048/-25932/-25696/-23040. So pattern B — a per-player "close-up state" block swapped in for that player's frame/turn, generalising tw_split's per-mode words swap and coop_cameras_lend's duration-based lend — matches what the code already does and what coop-todo 27 calls "level 3 (the close-up stepper, its prompt and the find copied per player)". Its cost is the gate hunt (B8): the words/close-up readers in the main loop and stepper have to be listed from the disassembly first (the user's stated condition), not found by play.
- Hybrid worth noting [inferred]: pattern A's renderer half (skip_views "this frame is player N's menu picture", only_view, Mem1Turn) is independent of the memory copy and could show a per-player close-up frame in one half without a memory copy, if the close-up stepper and words were run per player in real memory with pattern B swaps. The game-side precedent for running the SAME frame routine twice with different blocks in is tw (world and Tome frames alternating with kTwSwitches/TW_BLOCK swapped, 12932-12994), which also carries the known cost: the hidden list of what each mode owns (kTwSwitches grew to 13 words + the camera depth/index after the 2026-11-05 stuck-camera bug, two-tomes.md 59).
